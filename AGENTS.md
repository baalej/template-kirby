# AGENTS.md

Context and instructions for AI agents (Claude Code, Cursor, Copilot, Codex, Antigravity, etc.) working on this Kirby CMS project.

This file is the single source of truth. `CLAUDE.md` and any other tool-specific file must only reference it, never duplicate it.

---

## 1. About the project

This is a **base template for Kirby CMS projects**. It serves as the starting point for new sites, so the decisions made here get inherited by every future project. Always prioritize:

1. **Minimalism** — the simplest solution that solves the problem, with no unnecessary layers.
2. **Best practices** — idiomatic Kirby/PHP code, no hacks unless documented and justified.
3. **Consistent style** — a single formatting standard across the whole project.
4. **Good organization** — everything in the place Kirby expects; a predictable structure.
5. **Performance** — zero unnecessary JS/CSS, efficient content queries, no build-step overhead.
6. **Reusability** — reusable snippets, components, and fields before duplicating code.
7. **Maintainability** — code that's readable by someone else (or by you in six months) without extra context.
8. **Accessibility** — semantic HTML, correct contrast, keyboard navigation, and ARIA by default, not bolted on afterward.

## 2. Project structure

```
site/
├── blueprints/       # Content structure definitions (YAML)
│   ├── pages/
│   ├── files/
│   └── users/
├── config/
│   └── config.php    # Per-environment configuration
├── controllers/       # Data preparation logic for templates
├── languages/          # Only if the project is multi-language (see §2.1)
├── plugins/            # Local project plugins (not third-party)
├── snippets/           # Reusable components (header, footer, cards...)
│   └── components/     # Purely visual/reusable snippets
├── templates/          # One template per page type
└── models/             # Page models (business logic per page type)

content/                # Content (don't change structure without a matching blueprint)
assets/
├── css/
├── js/
└── fonts/
media/                  # Generated by Kirby, do not version-control
kirby/                  # Core, never modify
```

**Organization rules:**
- A snippet should never exceed ~150 lines; if it grows beyond that, split it into sub-snippets.
- Data logic belongs in **controllers** or **page models**, never in templates or snippets. Templates should only print/format, not compute.
- File and field names in `kebab-case` (e.g. `hero-section.php`, `project_gallery` → `project-gallery`).
- One blueprint per content type; avoid monolithic blueprints with dozens of fields when it can be modularized (see §6 for blocks vs. structure fields).

### 2.1 Multi-language

Not every project needs this — confirm with the project brief before adding language support. When it applies:
- Enable it in `site/config/config.php` (`languages => true`) and define languages in `site/languages/`.
- Never hardcode UI strings in templates or snippets; use `t('key')` translations even for small labels, so the project can go multi-language later without a rewrite.
- If the project is confirmed single-language, skip translation helpers entirely — don't add complexity for a case that isn't happening.

### 2.2 Asset organization

There's no bundler, so the folder structure inside `assets/` is the only thing keeping CSS/JS modular. The rule: **`assets/css/` and `assets/js/` mirror the PHP files they belong to, category by category.** A snippet's styles live at the same relative path as the snippet itself; a block's styles live in their own top-level category (blocks are treated as a first-class Kirby concept, not nested under snippets, even though the block templates technically live in `site/snippets/blocks/`).

```
assets/
├── css/
│   ├── base/                  # Reset, CSS variables, typography — loaded on every page, not tied to one snippet
│   │   ├── reset.css
│   │   ├── variables.css
│   │   └── typography.css
│   ├── snippets/               # Mirrors site/snippets/ 1:1 — header, footer, nav, components/, etc.
│   │   ├── header.css
│   │   ├── footer.css
│   │   ├── nav.css
│   │   └── components/
│   │       └── card.css
│   ├── blocks/                  # One file per Kirby block type (site/snippets/blocks/*.php)
│   │   ├── hero.css
│   │   └── text.css
│   └── templates/                # Page-type-specific styles that don't belong in a reusable snippet
│       └── project.css
├── js/
│   ├── snippets/
│   │   └── components/
│   │       └── gallery.js
│   ├── blocks/
│   │   └── hero.js
│   └── templates/
│       └── project.js
└── fonts/
```

**Naming rule:** a CSS/JS file's path mirrors the PHP file it styles/scripts, one level for one level:
- `site/snippets/header.php` → `assets/css/snippets/header.css`
- `site/snippets/components/card.php` → `assets/css/snippets/components/card.css`
- `site/snippets/blocks/hero.php` → `assets/css/blocks/hero.css` (promoted out of `snippets/` — see below)
- `site/templates/project.php` → `assets/css/templates/project.css`
- No `.php` file → no matching CSS/JS file. If nothing in `assets/` styles it, don't create a placeholder file "just in case."

**Why blocks get their own top-level category:** a block and a snippet component can reasonably share a name (a `card` block and a `card` component are a common, legitimate collision), and Kirby itself already treats blocks as distinct — with their own blueprint folder (`site/blueprints/blocks/`) separate from the rest of the schema. Keeping `assets/css/blocks/` separate from `assets/css/snippets/` reflects that. To keep it collision-proof at the CSS level too, block root classes get a `block-` prefix (see §3).

**Selective loading per template:** since nothing bundles these files together automatically, each template is responsible for declaring what it actually needs:
- `base/*.css` loads on every page — put it in the shared `<head>` snippet, not per-template.
- A template loads its own `templates/[name].css` (if it has one) plus one file per snippet it directly includes.
- If a template renders a `blocks` field, load all of `blocks/*.css` as one group — the editor can place any block type on that page, so there's no way to know in advance which ones will actually appear, and there's no bundler to split it further.

```php
<?php
$assets = [
    'base/reset.css', 'base/tokens.css', 'base/typography.css',
    'snippets/header.css', 'snippets/footer.css',
    'snippets/components/card.css',
    'templates/project.css',
];
?>
<?= css(array_map(fn ($file) => 'assets/css/' . $file, $assets)) ?>
```

Same pattern for `js()`, with `defer` and only the JS a given template's snippets/blocks actually need.

**Exception — plugins:** a plugin in `site/plugins/` keeps its own CSS/JS in its `assets/` folder and loads it from its own snippets (`$kirby->plugin('author/name')->asset('file.css')->url()`), so it stays self-contained and can be dropped into or removed from a project as a unit.

### 2.3 Analytics and cookie consent

The template ships `site/plugins/consent`: Google Analytics 4 behind a cookie banner. Use it — never write another banner or analytics snippet.

- **Enable:** set `'baalej.consent' => ['id' => 'G-…']` in `site/config/config.php`. Without an `id` nothing renders. Options (privacy page, banner texts) are listed with their defaults in the plugin's `index.php`; override them in config, never edit the defaults per project.
- **Already wired:** `snippet('consent/banner')` at the end of `<body>` and `snippet('consent/settings')` (the button that reopens the banner, required to withdraw consent) in the footer of `site/snippets/layout.php`. Keep both if the layout changes.
- **Any script that sets cookies or tracks visitors** (Meta Pixel, Hotjar, Tag Manager…) must only load after consent: add its loader next to `loadAnalytics()` in `assets/banner.js`, and its cookies to the cleanup on withdrawal. Never put it directly in a template or the `<head>`.
- **Styling** is per project: override `.consent` / `.consent-settings` in the project's own CSS, don't edit the plugin's `banner.css`.
- **Local testing:** keep the real `id` out of local environments (see the README). The markup/storage contract the JS relies on is documented at the top of `assets/banner.js`.

## 3. Code style

### PHP
- PSR-12 as the baseline.
- Use helpers like `kirbytext()`, `$page->field()->value()`, etc. — avoid direct array access or raw SQL.
- Always escape user-facing content: `<?= $page->title()->esc() ?>` instead of `<?= $page->title() ?>` when the value goes into HTML.
- Never hardcode text, paths, or IDs that should come from content or config.
- Comments only where the "why" isn't obvious — don't comment the obvious.

### HTML / Templates
- Always semantic HTML5: `<nav>`, `<main>`, `<article>`, `<section>`, `<header>`, `<footer>` instead of generic `<div>`s.
- 2-space indentation, double-quoted attributes.
- One snippet = one clear responsibility.

### CSS — BEM
- Class naming: `.block`, `.block__element`, `.block--modifier`. No exceptions, no mixing with utility classes.
- File organization (folders, one file per component/block/template) is defined in §2.2 — follow it, don't invent a different layout per project.
- **Block prefix:** BEM root classes for Kirby blocks get a `block-` prefix (`.block-card`, `.block-card__image`), while snippet components use the plain name (`.card`, `.card__image`). This avoids name collisions between a block and a component that legitimately share a concept, and makes it obvious in devtools whether markup came from editor-placed content or a fixed snippet.
- CSS variables (`:root`) for colors, spacing, and typography; no repeated magic values.
- Mobile-first: write the base CSS for mobile and add `min-width` media queries going up.
- Avoid `!important` except for explicit override utilities.
- Avoid nesting selectors more than 2 levels deep — BEM naming should make deep nesting unnecessary.

### JavaScript
- Vanilla JS only, no framework, no dependencies — this project has no bundler, so anything added must run directly in the browser as-is.
- `defer` on `<script>` tags, no blocking JS in the `<head>`.
- Progressive enhancement: the site must remain functional without JS whenever reasonable.
- Keep scripts small and scoped per feature (`assets/js/nav.js`, `assets/js/gallery.js`) rather than one large bundle file — since there's no build step, file boundaries are the only modularity we get.

## 4. Performance

No build tool, no bundler — CSS and JS are served as-authored. This makes discipline at write-time more important, not less:

- Serve assets through Kirby's `css()` / `js()` helpers, which automatically append a version query string based on file modification time — no manual cache-busting needed.
- Optimize images via Kirby's `$image->resize()` / `srcset()` — never upload unprocessed images directly into HTML.
- Load fonts with `font-display: swap` and preload only critical fonts.
- Minimize the number of content queries inside loops (`children()->filterBy()` outside the loop, not inside).
- Keep CSS/JS files hand-minified in spirit: no dead code, no unused selectors, no commented-out blocks left in production files.
- Don't reach for page caching by default — it's not part of this template's baseline. If a specific page genuinely needs it (heavy listings, external API calls), evaluate and document it in that project's own notes, not here.

## 5. Accessibility (non-negotiable)

**Qualitative guidelines:**
- Every interactive element must be keyboard-accessible (correct `tabindex`, no focus traps).
- Minimum AA contrast (4.5:1 for normal text, 3:1 for large text) — verify on any new color palette.
- Images with meaningful `alt` text (or `alt=""` if purely decorative), pulled from the content field when it exists.
- Forms with a `<label>` associated to each `<input>`, error messages announced (`aria-live` where it applies).
- Correct heading hierarchy (single `h1` per page, no skipped levels).
- Never remove the focus `outline` without replacing it with an equally visible focus style.

**Measurable threshold — before closing any task that touches markup or styling:**
- Lighthouse Accessibility score **≥ 95** on the affected page(s).
- **Zero critical/serious issues** reported by axe DevTools (or an equivalent automated checker) on the affected page(s).
- If a score below 95 or an axe issue can't be resolved immediately, it must be explicitly flagged and explained, not silently left — don't mark the task done "as is."

## 6. Reusability

- Before writing a new snippet, check whether an existing one can be parameterized (`snippet('card', ['title' => ..., 'image' => ...])`).
- Repeated visual patterns (buttons, cards, badges) live in `site/snippets/components/`, styled as BEM blocks.
- Repeated config (colors, breakpoints) centralized in one place (CSS variables or `site/config/config.php`), never copy-pasted across files.

**Blocks vs. structure fields — decide per project, not globally:**
- Use **Kirby blocks** when the editor needs to freely compose page layout (marketing pages, landing pages, blog posts with mixed content).
- Use **structure fields** when the layout must stay visually consistent and the editor only fills in data (team members, pricing tables, FAQs).
- Whichever is chosen for a given content type, document the choice briefly in that blueprint's YAML as a comment, so the next person (human or agent) doesn't have to guess why.

## 7. Common commands

No bundler — assets are edited and served directly. Typical workflow:

```bash
composer install          # Install PHP / Kirby dependencies
composer lint               # PHP linter (if configured, e.g. PHP_CodeSniffer)
```

CSS/JS require no build/watch step — edit files under `assets/css/` and `assets/js/` directly; Kirby's `css()`/`js()` helpers handle cache-busting automatically via file modification time.

---

## 8. What NOT to do

- Don't modify anything inside `kirby/` (the core).
- Don't commit `media/`, `.env`, or credentials.
- Don't introduce a bundler, framework, or build step to "solve" something plain CSS/JS already solves — that's a deliberate constraint of this template, not an oversight.
- Don't mix BEM with utility classes in the same project.
- Don't create new fields or blueprints without checking whether an existing one already covers the need.
- Don't skip validation/escaping of user content, even if "in this case there's no risk."
- Don't enable page caching as a default optimization — see §4.
- Don't load tracking or cookie-setting scripts outside the consent plugin — see §2.3.

## 9. Before marking a task as done

Check that the generated code meets:

- [ ] Semantic, accessible HTML (§5 qualitative guidelines)
- [ ] Lighthouse Accessibility ≥ 95 and no critical axe issues on affected pages (§5 threshold)
- [ ] No business logic in templates/snippets
- [ ] Reuses existing snippets/blocks/structures where possible
- [ ] CSS follows BEM, JS is plain and dependency-free (§3)
- [ ] New CSS/JS files are placed and named per §2.2 (mirrors the snippet/block/template they belong to)
- [ ] Template only loads the CSS/JS it actually needs (§2.2 selective loading), nothing extra
- [ ] No bundler, framework, or build step introduced
- [ ] Images optimized via Kirby, not raw
- [ ] Works without JS if the functionality allows it
